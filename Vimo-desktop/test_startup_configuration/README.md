# 启动与配置测试 SC

本目录负责模块二 AI 融合实践中的 Startup & Configuration（启动与配置）业务链路，覆盖 `TC-SC-001` 至 `TC-SC-005`。重点验证部署后的启动失败、配置校验和修复后重新初始化。

已实现 5 个业务用例、14 个参数化自动化检查，统一使用 Vitest 测试真实 TypeScript 业务入口。当前不需要额外 Python 检查，因此没有创建空的 pytest 配置。业务代码未修改；测试中保留不满足验收标准的真实失败。

在仓库根目录一键执行：

```powershell
node Vimo-desktop/test_startup_configuration/run_tests.cjs
```

也可执行 `npm.cmd test --prefix Vimo-desktop/test_startup_configuration`。运行器优先使用本目录依赖，否则复用现有 `test_communication/node_modules` 中的 Vitest 2.1.9；不依赖全局 Vitest。两处都未安装时执行：

```powershell
npm.cmd install --prefix Vimo-desktop/test_startup_configuration
```

每次运行生成独立的 `results/<UTC时间戳>-<进程号>/`，包含源码/测试 SHA-256、Git 版本、原始 Vitest JSON、完整控制台记录、JUnit XML 和按业务 ID 汇总的 JSON/CSV。JUnit 由原始 JSON 生成，规避 Vitest 2.1.9 内置 JUnit reporter 在多个软断言失败时的监听器警告。

退出码：0 为全部通过，1 为业务断言失败或未完成检查，2 为依赖、收集或运行器异常。不能以本阶段测试全部变绿作为完成标准；应先判断失败来自业务还是测试装置。

## 范围与框架约定

- 唯一业务分类标准是 SC；不再按前端、IPC、API、算法四层拆分用例清单。
- 测试 TypeScript / TSX 使用 **Vitest**；测试 Python 使用 **pytest**。
- 同一业务 ID 可以对应多个自动化检查；汇报时仍统计为一个业务用例，参数组合数和脚本执行数另外统计。
- 本目录不承担视频索引 VI、内容查询 VQ 或独立的状态恢复 SR 测试。服务恢复后的重新连接、配置修复后的重新初始化属于 SC 本身的验收范围。
- 测试调用真实业务源码，只隔离 Electron、网络、进程和高成本模型等外部依赖；测试目录中不复制业务实现。

## 用例与实现思路

### TC-SC-001 打包目录缺少后端可执行文件时立即失败

**目标：** 生产模式下后端可执行文件不存在时，启动立即返回失败，且没有启动进程或进入健康检查重试。

- 入口：`src/main/handlers/videorag-handlers.ts` 的 `startVideoRAGService`。
- 框架：Vitest，Node 环境。
- 设置非 development 模式，提供模拟的 `process.resourcesPath`，令可执行文件路径的 `fs.existsSync` 返回 false。
- 隔离 Electron、`child_process.spawn` 和 axios；不得真正启动后端或删除打包文件。
- 检查启动 Promise 拒绝、错误指向缺失文件、`spawn` 和健康请求均未发生，没有遗留重试定时器。
- “立即失败”以无需推进启动等待定时器即可失败判断，不使用脆弱的毫秒级耗时阈值。
- 源码已有文件存在性判断。本项属于部署阻断风险的必要验证，不能预设它一定失败。

### TC-SC-002 后端长期不可达时有限次数退出并支持重新连接

**目标：** 后端持续不可达时在约定预算内结束启动；服务恢复后，新一次启动尝试能够成功，旧重试不再运行。

- 入口：`startVideoRAGService`、健康扫描及初始化链路。
- 框架：Vitest，Node 环境，使用 fake timers。
- 首次让所有候选端口的健康检查失败，检查完整扫描轮次、总等待预算、失败结果及定时器清理。
- 随后让一个候选端口返回真实健康响应结构，提供合法配置和成功的初始化响应，再调用启动入口，检查恢复成功。
- 端口探测次数与完整扫描轮次分别记录；不能把扫描 20 个端口误认为重试 20 轮。
- 本次按 README 建议落实的测试预算为最多 3 轮完整扫描、总启动等待不超过 60 秒，统一定义在 `support.ts` 的 `policy` 中。这是本阶段测试目标，不是当前产品已有承诺或作业强制值。连接拒绝和每次请求耗时 5 秒的超时场景分别验证，时间均为虚拟时间。
- 健康检查恢复与初始化成功都需要满足，不能仅因为服务可达就判定应用可用。
- 当前源码设置 `maxScanAttempts = 1000000`，且存在初始化失败后仍返回服务启动成功的分支，重点验证这些分支。
- 不使用 `runAllTimers` 无限制跑完长期重试；分段推进虚拟时间并设置测试保护上限。

### TC-SC-003 配置 JSON 损坏或缺少必填字段后可修复并重新初始化

**目标：** 已存在但损坏或不完整的配置不能被当作可用配置；用户修复后，无需重启整个应用即可重新初始化。

- 入口：`src/main/handlers/settings.ts` 的配置加载 handler，以及 `videorag-handlers.ts` 中的配置加载和初始化链路。
- 框架：Vitest。必要的后端初始化契约补充使用 pytest，仍归本 ID。
- 分别提供截断 JSON、缺少 `storeDirectory`、缺少 `openaiApiKey`、缺少 `dashscopeApiKey` 的配置。每次只注入一个主要错误。
- 检查初始化被阻止，有可识别的配置错误或待配置状态，不启动索引或查询，不向后端提交不完整配置。
- 在同一次测试中替换为合法配置后重新初始化，检查重新读取配置、成功状态，以及旧错误被清除。
- 当前 settings 加载可能将读取/解析异常静默回退为默认值；必须继续验证应用是否阻止初始化，不能仅以 `load-settings` 返回 `success: true` 判断缺陷。
- 阶段一的“配置文件不存在时返回默认值”只作参考，本项重点是已有文件异常和修复后的状态迁移。

### TC-SC-004 sk- 开头但实际无效的 API Key 不能通过验证

**目标：** 符合字符串前缀规则不等于服务端认证有效；认证失败必须返回验证失败。

- 入口：`src/main/handlers/settings.ts` 注册的 `test-api-key` handler。
- 框架：Vitest。捕获 `ipcMain.handle` 注册回调，调用实际 handler。
- 使用明确的假密钥，例如 `sk-test-invalid`；在实际 HTTP/SDK 调用边界模拟服务端认证失败（401），不能 Mock 被测验证 handler 的最终结果。
- 检查发生真实验证逻辑对应的外部调用、认证失败没有转为成功、返回可理解错误且不暴露完整密钥；增加认证成功的正向对照，避免实现永远返回失败也能通过。
- 网络超时应报告验证未完成或网络异常，不能当成认证成功；也不能直接证明密钥无效。
- 当前 handler 只检查 `sk-` 前缀后返回成功，尚未进行服务端验证。正式测试应保留上述业务期望，失败后再单独设计修复，不修改断言迎合现状。
- 无真实密钥、无付费调用；具体认证请求及客户端接口在修复设计时确定，避免测试预先绑定一个虚构接口。

### TC-SC-005 初始化阶段识别模型文件缺失或存储目录不可写

**目标：** 初始化阶段识别必需文件和写入能力的问题，不将故障推迟到首次分析才暴露。

- 入口：`videorag-handlers.ts` 的初始化链路。后端初始化补充验证入口为 `python_backend/videorag_api.py` 的 `/api/initialize`。
- 框架：TypeScript 检查使用 Vitest；若增加 Python 检查则使用 pytest。
- 两个独立子场景：模型路径不存在；模型存在但存储目录可读、不可写。分别构造环境，不能让模型缺失掩盖权限问题。
- 模型缺失时模拟文件访问返回 ENOENT；不可写场景保持存在性/读取检查成功，只在写权限检查或实际写入探测时返回 EACCES。
- 检查初始化整体失败、错误指向相应资源、不会报告可用或发起分析；修复路径或权限后可重新初始化。
- 当前源码已检查模型路径可访问，但存储目录检查主要是默认 `access`/必要时 `mkdir`；目录存在不代表能够写入。
- 不能通过把所有 `access` 都设为失败来冒充“目录存在但不可写”；无需修改用户真实目录权限。

## 隔离与复现

1. Vitest 隔离 `electron`、axios、`child_process` 和文件系统边界。保留业务控制流程，不 Mock 初始化函数的成功/失败结果。
2. 每例重新加载包含模块级状态的模块，恢复环境变量、`process.resourcesPath`、Mock 和定时器，避免上一次服务状态污染下一例。
3. 初始化测试可参考现有 `test_communication` 的 handler 捕获方式，不把该目录的旧结果当作本阶段执行结果。
4. 若引入 pytest，显式加载 `python_backend/videorag_api.py`，并验证模块的 `__file__`；不要默认导入 `test_videorag_api/videorag_api.py` 副本。
5. 单元测试以依赖替身模拟部署条件，不声称已经完成真实打包环境验收。真实部署复核后另存证据。

## 实施与执行说明

已完成可执行文件缺失、配置修复、模型缺失/权限、API Key 和定时器恢复测试。运行器固定检查收集数量，避免未收集到测试却产生通过报告。分组检查数分别为 SC-001：1、SC-002：4、SC-003：4、SC-004：3、SC-005：2。

Vitest 在 Node 环境中使用 globals 注入测试 API；模块使用前重置，文件系统保持必要的真实权限常量，业务操作落到内存替身。没有真实后端、模型、密钥验证请求或权限修改。API Key 的 401/成功/超时响应目前未被生产代码消费，因为它没有外部验证调用；测试将“未发起验证”明确判为失败，不声称已完成真实认证实验。

本次复用了 `test_communication` 中已安装的 Vitest 2.1.9，没有安装新依赖或修改其他目录的锁文件。启动测试中的预算失败通过状态观测断言，不无限 await 未结束的 Promise；每例最终清理所有虚拟定时器。

## 当前业务验证结果

在 Node.js 22.13.1、Windows、Vitest 2.1.9 环境中，14 个检查为 6 通过、8 失败；没有跳过或预期失败标记。业务 ID 共 5 个，2 个全部通过，3 个包含失败。最终报告位置及调试过程见 [实施记录](evidence/implementation.md)。

| 业务 ID | 通过/检查数 | 结论 |
| --- | --- | --- |
| TC-SC-001 | 1/1 | 缺失后端文件可立即失败，未启动进程或扫描 |
| TC-SC-002 | 0/4 | 重试未在预算内结束；恢复后旧尝试也初始化；初始化失败仍报告成功 |
| TC-SC-003 | 4/4 | 已测的损坏配置和缺字段均可阻止重新初始化，并通过保存修复后成功 |
| TC-SC-004 | 0/3 | 前缀检查后直接成功，没有服务端认证请求，连正向对照也无法证明密钥有效 |
| TC-SC-005 | 1/2 | 模型缺失可识别并恢复；可读但不可写目录仍通过初始化 |

8 个失败检查不是 8 个独立缺陷。SC-003 的重新初始化入口通过，与 SC-002 的启动包装器吞掉初始化失败同时存在，并不矛盾。本次为隔离环境下的业务验证，未进行真实打包部署或付费接口验证。

## AI 实践记录与完成标准

- 保存提示词、原始 AI 输出、人工审核、脚本修改原因、源码提交号和执行日志。区分 AI 新生成、已有场景扩展及人工补充。
- 5 个业务 ID 均有可定位的自动化结果；参数组合与业务数量分开报告。
- 预期失败不能使用无依据的 skip/xfail 隐藏；导入错误、超时和未收集到用例不计为通过。
- 对确认缺陷保留修复前失败、修复后通过及相关回归证据。尚未执行时不填写通过率和缺陷数量。
