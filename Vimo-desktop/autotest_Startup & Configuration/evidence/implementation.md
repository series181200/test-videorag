## 调试过程

1. 初次执行发生 Vitest hoisted 变量直接导出的收集错误，尚未执行业务测试；修改为内部 hoisted 变量加普通导出。
2. 第二次发现文件系统 Mock 缺少权限常量，导致访问装置抛异常、配置回退默认值。这是测试装置错误，不能计入业务缺陷；保留真实 fs 常量后，配置修复与模型缺失检查通过。
3. 核查多个失败报告中的 MaxListenersExceededWarning，通过 Node 的 trace-warnings 定位到 Vitest 2.1.9 内置 JUnit reporter 为软断言错误格式化时注册监听器。运行器改为保留原始 JSON，再自行生成 JUnit，没有提高监听器上限或隐藏警告。
4. 最终完整执行仍保留业务断言失败；没有修改断言迁就源码，没有 skip/xfail，没有声称业务已经修复。

## 结果与可复现观察

14 个检查收集完整，6 通过、8 失败，运行器退出码为 1。5 个业务 ID 中 SC-001、SC-003 全部通过；SC-002、SC-004、SC-005 含失败。失败检查按根因去重后再形成正式缺陷清单。

| 关联 ID | 隔离环境中的观察 | 实际验证范围 |
| --- | --- | --- |
| SC-001 | 后端文件缺失立即拒绝，无 spawn、HTTP 请求或遗留定时器 | 模拟打包路径，未操作真实打包目录 |
| SC-002 | 连接拒绝时虚拟 60 秒内发生 340 次探测，启动仍 pending；慢请求场景也未在总预算结束 | 真实调度逻辑与模拟网络时延 |
| SC-002 | 服务恢复后旧尝试转为成功，新旧尝试各初始化一次 | 同一模块内连续启动，未重置业务状态规避问题 |
| SC-002 | 服务可达但配置损坏时，启动 handler 仍返回 success=true | 真实启动包装器和配置加载链路 |
| SC-003 | 损坏 bootstrap JSON 或缺失必填字段均阻止重新初始化；通过真实 save-settings 修复后成功 | 4 个参数场景；不外推为所有配置损坏形式均通过 |
| SC-004 | 3 种预设认证结果均没有触发外部请求，handler 仅凭 sk- 前缀返回成功 | 验证逻辑缺失；预设 401/200/超时并非真实服务响应 |
| SC-005 | 模型文件缺失可拦截并恢复；目录存在但写权限不足时仍调用 /initialize 并成功 | 模拟权限边界，未修改用户目录权限 |
